## 1. 背景与设计约束

用户要求：飞书通道审批必须发**授权卡片**（不是 dsh-im 文本审批）；web GUI 通道审批维持浏览器弹窗，**两通道绝不混淆**；**dsh-im 源码禁止修改**（升级继承）。

方案选型：曾评估方案 B（改 dsh-im 内部实现）→ 继承性差被否；最终采用**方案 C**（DSH 引擎层 `extensions/approval-feishu` 插件路由挂载 + 独立工作区 `auth_request.py` 发卡脚本），dsh-im 仅消费状态文件 + 点击后 patch 原卡，dsh-im tgz 升级天然不影响。

dsh-im 侧职责（本 PR）：接收 `card.action.trigger` 回调 → 写状态文件 → `message.patch` 原卡为授权结果。授权卡的**发卡、有效期、超时灰化**由 `auth_request.py` 负责，dsh-im 不感知。

## 2. 端到端链路

```
approval/request (DSH 引擎, 飞书会话)
  → approval-feishu 插件 (只拦 agentPreset 匹配 *-feishu)
  → auth_request.py 发卡 (lark-cli im +messages-send, Card 1.0 横排按钮)
  → 用户点击 (card.action.trigger)
  → dsh-im bridge #handleAuthCardAction   ← 本 PR 修复
  → 写状态文件 authDir/<auth_id>.json
  → message.patch 原卡为 ✅已授权/❌已拒绝 (JSON string)
  → auth_request.py 轮询状态文件 → exit 0/1
超时 (timeoutSec 默认 300s)
  → auth_request.py 先写状态文件 status=timeout (逻辑防线)
  → patch 原卡为 ⏰已过期 灰化卡 (按钮 disabled, UI 防线)
```

## 3. 卡片 UX 演进（2026-08-27 三轮优化，全部在 auth_request.py）

### 3.1 有效期显示
卡片正文追加 `⏱️ 有效期 **{timeout} 秒**（截止 HH:MM:SS），超时自动失效`。timeout 来自 `--timeout` 参数（默认 300s = 卡片等待 + 展示有效期）。

### 3.2 超时自动更新
新增 `patch_card_expired(auth_id, msg_id)`：超时后 `lark-cli api PATCH /open-apis/im/v1/messages/{message_id}` 更新原卡为过期态。best-effort，失败不影响主流程（逻辑防线兜底）。

### 3.3 按钮横排（Card 2.0 → Card 1.0 迁移）
**根因**：Card 2.0（`schema:"2.0"` + `body.elements`）**不支持** `{"tag":"action"}` 容器，按钮只能竖排；Card 1.0（顶层 `elements` 数组）支持 action 容器 → 按钮一行横排。
- Card 1.0 按钮携带 `value` 字段（`{auth_id, decision, grant}`）——dsh-im `#handleAuthCardAction` 读 `event.action.value` **原生兼容**（实测点击闭环无损）。
- Card 1.0 还使用 `"config":{"wide_screen_mode":true}` + 按钮 `type: primary`。

### 3.4 超时灰化 disabled
patch 过期卡时**保留按钮但全部 `disabled: true`** + `disabled_tips:"授权已过期，请重新发起"`，header 变 `grey` + 「⏰ 已过期」提示。飞书官方按钮原生支持 `disabled`（Boolean，默认 false）。

## 4. 双层防线（超时后点击双重拒绝）

| 层 | 机制 | 位置 |
| --- | --- | --- |
| ① 逻辑层 | 状态文件先写 `timeout`；dsh-im `#handleAuthCardAction` 见 `status !== 'pending'` 直接 return | auth_request.py main() 顺序 + bridge.mjs 已有检查 |
| ② UI 层 | patch 灰化 disabled 按钮，视觉不可点 + disabled_tips 提示 | auth_request.py patch_card_expired |

**顺序铁律**：必须**先写状态文件 timeout，再 patch 卡片**。若反序，patch 期间（subprocess ≤30s）状态仍 pending，用户点击会被 dsh-im 接受写 approved——竞态漏洞（已修复，原实现存在此 bug）。

## 5. schema 匹配铁律

飞书 `message.patch` **要求 patch 卡片与原消息 schema 一致**：

- Card 1.0 原消息 → 必须 Card 1.0 结构 patch（`{config, header, elements}`）
- Card 2.0 原消息 → 必须 Card 2.0 结构 patch（`{schema:"2.0", header, body.elements}`）
- 不一致 → 错误码 **230099**（"Failed to create card content, parse card json err"）

`patch_card_expired` 内置容错：先试 Card 1.0，stdout 含 230099 自动改 Card 2.0 结构重试（按钮 disabled 同构）。

## 8. dsh-im 升级继承与恢复清单

方案 C 三处改动均在 dsh-im 之外，dsh-im tgz 升级天然不影响：

1. DSH 引擎 `extensions/approval-feishu`（upgrade-dsh.sh --backup/--restore 保护）
2. `$DSH_HOME/profiles/{web,headless}/cordis.patch.yml`（升级天然安全）
3. DSH 工作区 `scripts/auth_request.py`（独立工作区）

若升级后发现飞书审批不走卡片，按序检查：`dump-config` 核对 approval-feishu 在 approval-policy **之前**且 feishuPresets 存在 → 检查/重建 `lib/index.js` → 补 `node_modules/@deepseek-ai/dsh-approval-feishu` symlink → 确认 auth_request.py + lark-cli 可用 → 重启 dsh-web → E2E 点卡复测。

## 9. 领域语言

- **授权卡片**：发往飞书的交互式卡片，按钮携带 `{auth_id, decision, grant}` 回调值。
- **状态文件**：`authDir/<auth_id>.json`，`status` ∈ pending/approved/denied/timeout；dsh-im 写 approved/denied，auth_request.py 写 timeout 并轮询。
- **灰化**：按钮 `disabled:true` + `disabled_tips`，视觉禁用且点击无响应。
- **双层防线**：逻辑层（状态文件）+ UI 层（disabled 灰化），超时后点击双重拒绝。
